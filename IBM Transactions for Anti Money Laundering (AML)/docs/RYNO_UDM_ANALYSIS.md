# Ryno HI-Small UDM Conversion: Descriptive Comparison

## Purpose and scope

This note records how Ryno's supplied conversion outputs differ from the
complete HI-Small source. It is descriptive analysis, not a model evaluation
or a claim about a production NICE Actimize installation.

The original HI-Small transaction source contains **5,078,345 payment rows**;
its account file contains **518,581 account records**. The source transaction
CSV used for the conversion has the same SHA-256 as the HI-Small source already
staged in this project. The full source remains available locally under
`Ryno Analysis(IBM)/` and `archive/`; the large CSVs are excluded from Git.

## Conversion populations

| View | Payment count | Account-side legs | Positive payments | Important scope |
|---|---:|---:|---:|---|
| Full HI-Small source | 5,078,345 | Not converted to legs | 5,177 | Complete transaction-row population; positive label rate is about 0.102%. |
| Ryno top-20-bank UDM output | 1,034,599 | 1,216,251 | 898 | Twenty selected banks, bank 70 excluded, tail excluded; positive labels are in a separate file. |
| Ryno Bank-12 sanitised output | 113,744 | 121,626 | 158 | One-bank view with the supplied 12-attribute schema; source tail retained. |

These are not interchangeable populations. The full source counts one payment
per row, whereas UDM output counts one debit or credit event per in-scope
account. A payment with both accounts in scope can therefore produce two legs.
Bank filtering and date-tail treatment also change which information and labels
are visible. Do not compare vendor performance across these outputs as if they
were the same frozen benchmark.

## What the outputs contain

- The top-20 conversion has **763,712 debit legs** and **452,539 credit legs**.
  It reports 1,088 positive legs and 898 positive payments; 646 positive
  payments are identified in the supplied pattern annotations. The manifest
  records 274 tail rows dropped.
- The Bank-12 conversion has **79,754 debit legs** and **41,872 credit legs**.
  It reports 165 positive legs across 158 positive payments. Labels are
  separate from the transaction messages.
- The source CSV has 11 fields. The sanitised UDM messages use the requested
  12-field attribute order and create one message per account leg. This
  transformation is not a byte-for-byte representation of the original
  payment row.

## Twelve requested attributes

| Required attribute | Source or transformation | Interpretation |
|---|---|---|
| Unique Identifier for the transaction | Generated from source row ordinal and D/C leg | New surrogate; not IBM-issued. |
| Account Key | In-scope bank ID + account number | Composite key; account number alone is not unique. |
| Transaction Date/Time | Source `Timestamp` formatted as local time | No timezone was supplied. |
| Transaction Type | Payment Format × account-leg direction | Derived code; not a source business transaction code. |
| Transaction Direction | Payer debit D and/or beneficiary credit C | Changes the unit from payment to account-side event. |
| Transaction Amount in Original Currency | D: `Amount Paid`; C: `Amount Received` | Keep each amount paired with the currency on the same side. |
| Original Currency Code | D: `Payment Currency`; C: `Receiving Currency` | Normalized currency code; Bitcoin is represented as XBT. |
| Transaction Amount in Account Currency | ZAR assumption plus implied FX × 17.50 ZAR/USD | Synthetic estimate; confirm account currency and approved FX. |
| Transaction Branch | Deterministic home/virtual branch generated by rule | Fabricated; HI-Small has no branch field. |
| Opposite account number | Account number from the other endpoint | Direct counterparty value for that source payment. |
| Opposite bank | Bank ID from the other endpoint, normalized by default | Synthetic bank key, not a real routing identifier. |
| Opposite country code | Inferred from the other bank's name | Heuristic; replace with trusted country reference data. |

The **Ryno Field Mapping** worksheet expands this table with the JSON key,
Ryno's specific transformation, and an action/caveat for each field.

## Assumptions that need confirmation

The Bank-12 output adds values not present in the HI-Small source:

1. **Account currency and FX:** every account is treated as ZAR. A 17.50
   ZAR/USD assumption is used with implied HI-Small rates. Ryno describes this
   as an approximation, not an official historical rate.
2. **Transaction branch:** branch identifiers are synthetic and deterministic.
   Cash/cheque uses an account's assigned home branch; electronic legs use a
   virtual branch unless a different mode is selected.
3. **Timezone:** the source timestamps have no timezone. The sanitised output
   writes them as local time.
4. **Bank-12 geography:** the manifest marks 61,704 of 121,626 legs as
   cross-border, based on the bank-country mapping. Ryno notes that Bank 12 is
   a US bank, so this is not representative of a South African-only
   institution.

None of these generated fields should be presented as source facts. Obtain
approved account-currency, FX, branch, timezone, and country references before
using equivalent fields in a real-system test.

## Benchmark and UDM interpretation

Ryno's notes explain that a single-bank subset loses counterparty activity
unevenly while labels remain globally defined. The notes also cite
multicurrency relationships in 216 of 370 pattern annotations and 38 of 54
cycles; those figures are cited from the supplied notes and have not been
independently recomputed here.

Account-leg normalization is useful for UDM-style account and party
aggregation, but linked transaction structures—ordered chains, cycles,
gather/scatter shapes, shared counterparties, and cross-currency hops—may
become implicit or unavailable in a UDM-only feed. Preserve source transaction
keys and linked-leg relationships, and test required patterns as named
permutation cases. Do not assume a UDM-only feed is a complete representation
of the original benchmark.

## Reproducibility and attribution

The conversion counts and parameters are recorded in the local Ryno
`top20/manifest.json` and `sanitised_bank12/manifest.json`; those manifests are
tracked in this project. Ryno's original scripts, notes, specification, and
full input datasets remain in the local `Ryno Analysis(IBM)/` folder and are
not redistributed in this repository. Confirm permission and applicable
licensing before publishing or sharing those original materials.
